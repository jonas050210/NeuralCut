# QLoRA Training on the Home PC (RTX 4060 Ti 8 GB)

Optional, offline, and entirely separate from the NeuralCut app. The app
never trains, never downloads models, and never promotes adapters
automatically.

## Recommended base model (verified)

**`Qwen/Qwen3-4B-Instruct-2507`** — Apache License 2.0 (verified on the
Hugging Face repo LICENSE file, 2026-10-24), 4.0B parameters, HF
safetensors format, needs `transformers>=4.51`. Use the HF repo id (or a
local HF-format directory). **GGUF files cannot be trained** with this
stack — they are for Ollama/llama.cpp inference only. The model is
downloaded by the training run itself from Hugging Face (~8 GB); nothing
is downloaded before you pass `--confirm-training`.

## Memory budget (planning estimates, not measurements)

4-bit NF4 weights ≈2.2 GB · LoRA optimizer/gradients ≈0.6 GB ·
activations (grad checkpointing, seq 2048, batch 1) ≈1.0 GB · CUDA
context ≈0.8 GB → **≈4.6 GB of 8 GB**. If you hit OOM: lower
`--max-seq-len` to 1024, keep batch 1, raise
`gradient_accumulation_steps` in the job config.

## Setup (Windows home PC)

```powershell
cd <NeuralCut checkout>
.\scripts\setup.ps1                 # app env (only needed for benchmarks/UI)
.\scripts\setup_training.ps1        # creates .venv-training (torch cu124 + training deps)
```

`setup_training.ps1` installs PyTorch from the CUDA 12.4 wheel index,
then `requirements-training.txt`. The app venv and the packaged Windows
app are untouched by this.

## Workflow

```powershell
# 1) Persist the frozen benchmark dataset from the app (optional; built-in default exists)
#    In the app UI: Self-Improvement -> Run baseline benchmark (writes reports),
#    or via API: POST /api/v1/improvement/dataset/persist

# 2) Preflight: deps, CUDA, VRAM estimate, dataset validity (no downloads)
.\.venv-training\Scripts\python.exe -m neuralcut.training.train_qlora --preflight

# 3) Optional dry run: validates data, writes SFT files, prints the plan
#    Use a separate directory from the actual training run.
.\.venv-training\Scripts\python.exe -m neuralcut.training.train_qlora --output adapters\orchestrator-dryrun

# 4) Real training (downloads the base model on first run; hours-scale on a 4060 Ti for this tiny dataset)
#    Pick a new, empty directory for every fresh run. This command is an example.
.\.venv-training\Scripts\python.exe -m neuralcut.training.train_qlora --output adapters\orchestrator-2026-10-25-run1 --confirm-training
```

## Data rules (enforced in code)

- SFT traces are generated by the **deterministic builtin planner** on the
  synthetic benchmark contexts (train split for training, val for eval).
- **Held-out cases are never exported** — requesting them raises, and the
  config validator rejects `held_out` in train/eval splits.
- Outputs: `adapters/<name>/data/sft_{train,eval}.jsonl`,
  `checkpoint-*` per epoch, `adapter/` (final LoRA adapter),
  `training_metrics.json` and `training_manifest.json` (base model,
  license, config, dataset fingerprint, seed, resume info, metrics file,
  evaluation status).
- `training_metrics.json` is written as soon as `trainer.train()` returns
  (train result metrics, `global_step`, full trainer log history) and
  rewritten after the final evaluation. If that evaluation cannot run,
  the file records `evaluation: null` plus the `evaluation_error` instead
  of losing the run's metrics; `training_manifest.json` is written last,
  after the adapter, so its presence means the run finished completely.

## Failure recovery

- Fresh training refuses a non-empty output directory, so existing
  adapters and checkpoints are never silently overwritten. Use a new
  output directory for another fresh run.
- Interrupted run → explicitly resume an incomplete checkpoint with
  `--resume` (latest) or `--resume checkpoint-<step>`, together with
  `--confirm-training`. Completed checkpoints cannot be resumed; use a
  new output directory instead.
- Training loss is logged each step and evaluation runs at each epoch;
  `training_metrics.json` records final train/evaluation metrics and the
  trainer log history alongside `training_manifest.json`. Metrics survive
  a failed final evaluation or failed adapter save — only the manifest
  (written last) is then missing, and the metrics explain why.
- Preflight failures list exactly which dependency is missing; the app
  installation is never affected.

## From adapter to production (human-gated, unchanged)

1. Register the adapter as a candidate configuration in the app's
   Self-Improvement view (model route pointing at your local endpoint
   serving the merged/adapter model).
2. Run routine evaluation (train/val), then the explicit **gate
   evaluation** (held-out, audit-logged).
3. Promote only with your named reviewer + spot-check confirmation;
   rollback is one action. Nothing promotes or overwrites automatically.

## What is verified vs not

- Verified here (CPU, mocked stack): CLI dry-run, preflight reporting,
  dataset/split enforcement, SFT trace generation, VRAM estimator,
  checkpoint-resume logic, adapter-save + manifest wiring, and metrics
  persistence (written before the manifest, kept when evaluation fails).
- **Not verified:** any real CUDA/QLoRA run, real model quality, actual
  VRAM/time on a 4060 Ti, TRL API drift against the pinned ranges. The
  first real run is yours, with `--preflight` first.
